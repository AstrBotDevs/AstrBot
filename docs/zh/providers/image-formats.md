# 图片处理

`build_main_agent` 在图片描述和 Agent 初始化前处理初始图片，包括普通附件、引用图片及插件 `ProviderRequest` 中的图片，直接调用构建函数也适用。请求 Hook 执行后，流水线只检查新增的图片引用；已有引用复用处理结果，不再次检查文件。

## 大小限制与格式

- 模型图片预处理时，原始图片文件超过 **64 MiB** 则在读取内容和解码像素前跳过；原因与保留的原图路径会保存到历史。另向模型提供临时建议：使用可用的文件读取工具，或请用户重发较小的图片，这段建议不保存到历史。小于等于 64 MiB 的图片正常处理。
- 模型使用的单张图片文件**严格小于 512 KiB**（524,288 字节）。限制针对 Base64 编码前的图片文件，不是整个请求体。
- 在管理面板的**配置文件**页面搜索**输入图片最大边长**，对应 `provider_settings.image_compress_options.max_size`，默认 1280 像素。初始图片保持宽高比，小图不会放大；为满足文件体积限制，必要时会进一步缩小。Hook 新增图片同样按配置限制最长边、处理格式和动图，并应用 64 MiB 输入上限和严格小于 512 KiB 的输出限制。
- 方向正常、像素尺寸及文件体积均合规的 JPEG/PNG 保留原始字节。其余静图修正方向后编码为 JPEG；含透明度的图片输出 PNG，即使需要进一步缩小也保留透明通道。
- GIF、动画 WebP、APNG 等动图均匀选取最多 9 帧，包含首尾动画帧，生成白底 3×3 拼图。不足 9 帧的格子留白，APNG 的独立封面不参与采样。
- 重新编码时移除不必要的元数据；与输出色彩空间兼容、且不影响体积达标的色彩配置保留。

CUA 会话中的用户输入图片也遵守这些限制；截图及其他工具返回的图片继续使用各自的处理逻辑。

## 配置项变化

| 原配置项 | 现在的行为 |
| --- | --- |
| 启用图片压缩（`image_compress_enabled`） | 已移除，当前输入图片始终处理。 |
| 压缩质量（`image_compress_options.quality`） | 已移除，自动控制输出体积。 |
| 最大边长（`image_compress_options.max_size`） | 更名为“输入图片最大边长”，同时遵守严格小于 512 KiB 的文件体积限制。 |

旧配置文件中遗留的启用开关和 JPEG 质量值不再影响图片处理。

## 原图路径与文件清理

图片处理阶段统一生成普通的 `Image N` 文本说明，包含原图路径，并标明是否来自引用消息。序号按 Hook 和过滤之后的图片顺序生成：额外图片内容块在前，`image_urls` 在后。请求实体和消息模型不新增附件元数据。引用来源和成功生成描述的图片由对应处理步骤直接传递，不解析提示文本推断状态；Hook 后只更新本次流程自己生成的提示对象，保留插件传入的文本。跳过的图片只保留原因和原图路径，不占图片序号；动图会标明已转换为九宫格。交给图片描述模型处理的图片标为已转文字描述，不占主请求的图片序号。

`image_urls` 及图片内容块直接复用合规的本地 JPEG/PNG 文件，不创建工作副本；需要转换的图片才使用处理后的预览文件。提供给模型、供工具读取文件的附件说明仍然指向**原始图片路径**，不会替换为预览路径。原始文件和事件中的图片组件均不被覆盖。

模型预览文件归当前事件所有，事件完成、失败或取消后清理，不再保留跨请求图片转换缓存。同一请求中重复出现的图片引用复用同一份预览，请求 Hook 前后的准备过程也会去重。

成功本地化的附件原图，包括引用图片，不随事件结束删除。临时目录中的原图仍受 `temp_dir_max_size` 容量清理约束，不属于永久存储。请求收集失败时，尚未成功接管的源文件仍按事件临时文件清理。

显式关闭持久图片上下文时，旧兼容路径会在预览删除前将模型图片以 Base64 data URI 写入历史，且不自动整理旧历史。默认路径保存图库引用，并在继续旧会话时迁移可恢复图片。无法读取的图片会跳过，不影响其他文字和正常图片；取消、资源耗尽及程序错误不会被当作坏图忽略。

第三方 Agent 后端、绕过主 Agent 构建函数直接调用 provider，以及工具返回的图片，不属于本次输入图片处理范围。

图片上下文的自动描述允许 JSON 前后空白、开头 BOM、单个完整的 JSON/无语言 Markdown 代码围栏，以及不含结构括号的前后说明。唯一完整对象之后（若有围栏，则在结束围栏之前）仅剩多余闭合括号和空白时，可忽略该尾部；不会补齐或修改对象内部。字符串里的未转义换行、回车和制表符可直接解码并保留，其他未转义 C0 控制字符仍拒绝。仍要求唯一完整的 JSON 对象、图片 ID 精确对应且没有重复键；截断、多对象、纯文字或不明确的包装不会入库，也不会触发额外的模型修复调用。描述失败与原图保存是独立状态。

## 持久图片上下文

持久图片上下文默认启用（`provider_settings.image_context_enabled=true`）；旧配置缺少该字段时也按启用处理。显式设置 `false` 可关闭。原图保存在数据目录的 `image_assets/`，历史只保留引用及可用描述；普通文字聊天无需反复发送历史图片。模型需要辨认旧图细节时才读取视觉内容，发回原图则使用当前会话的图库引用，无需提供磁盘路径，也不调用视觉模型。

图库不设置总容量或单张原图字节配额；保留每帧2000万像素、每张100帧及文件有效性检查。视觉请求不设置图片张数或Base64合计字节上限，仍沿用 AstrBot 原有的模型图片预处理规则（64 MiB 输入、严格小于512 KiB的预览输出）。描述失败不等于原图保存失败；待处理描述不会替换旧的有效描述。会话删除或解除引用后按生命周期策略回收，尚未关联的孤儿原图保留供显式维护。

2026-09-23的QQ/OneBot实测中，12张独立原图均完成文件哈希核验和描述保存；两个会话历史为77907 B和8278 B，均无内嵌图片Base64。连续三轮文字聊天和一次10图引用发送均为0视觉调用。这是该测试实例的观测，不是模型准确率、所有平台兼容性或生产性能保证。

四图历史的离线对照中，引用正文为52438 B，替换为等原图大小Base64占位后的正文为1469926 B；同一Python解析/序列化对象流程估算为0.247 MiB与5.654 MiB。这不是旧版进程RSS实测，不包含SDK、图片解码和平台发送缓冲，也不能作为整机内存节省比例。

后台记录主回答、描述、重看和摘要的实际调用及已报告用量。未知用量不等同于零；本功能不增加统计界面。

## 图片上下文与旧会话整理

持久图片上下文现在是内置 Agent 的默认图片处理方式，工具产图也走同一管理流程。升级前应保留完整备份。上述 Base64 历史写入是显式关闭 `provider_settings.image_context_enabled` 时才使用的旧兼容路径，不再是默认行为。

升级后第一次继续一个旧会话时（未显式关闭图片上下文），系统会在后台整理该会话里的旧图片，不弹确认框，不在启动时扫描全库，也不调用模型重新识图。只恢复内嵌图片和 AstrBot 临时目录里仍可读取的缓存；这些字节可能已经缩小或抽帧，因此标为“旧模型输入”，不能当作原始上传文件。描述先保持待处理，需要时再按重看预算查看。

迁移使用会话快照校验：历史及图片引用一起提交，改写后的正文也必须在在线读取上限内。坏图、过期缓存、不支持的远程地址、存储失败或并发改写会阻止此次整理，旧会话保持不变，本轮也不会继续覆盖旧历史。不会自动访问历史里的远程 URL 或任意服务器文件。下次主动发消息可以重新尝试；一次请求内部不循环重试。失败前已发布但未关联的图片仍占图库空间，按既有孤儿维护规则清理。

在线读取与普通迁移的历史正文上限为 **16 MiB UTF-8 字节**，在数据库正文进入 Python 之前检查；这是历史正文限制，不是图库容量限制。超限会话仍保留，列表、改名与删除不必加载正文；打开历史、继续聊天、分支、迁移和在线导出会明确拒绝。在线完整备份遇到这类正文也会失败，不会用空表冒充成功备份。本次改动不包含超限历史的离线迁移工具；升级前应停机复制整个 `data` 目录保留完整副本。

关闭开关不会把已经迁移的引用自动还原为 Base64。旧版 AstrBot 未必认识图片引用，回退旧版应恢复迁移前的完整备份；便携图片包用于带走会话资料，不是数据库降级或自动导入工具。
