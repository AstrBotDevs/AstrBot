# Model input images

The main-agent builder (`build_main_agent`) prepares initial input images before agent initialization. This covers ordinary attachments, quoted images, plugin `ProviderRequest` images, and direct calls to the builder. After `OnLLMRequestEvent`, the pipeline processes only newly introduced image references; existing references reuse their prepared results without another file check.

## Limits and formats

- During model-image preprocessing, original image files larger than **64 MiB** are skipped before reading their contents or decoding pixels. The omission reason and retained original path are saved in history. A temporary notice suggests the file-reading tool if available or asking the user to resend a smaller image; this advice is not saved. Files up to and including 64 MiB are processed normally.
- Each prepared image file is **strictly smaller than 512 KiB** (524,288 bytes). This limit applies to image bytes before Base64 encoding, not the entire request.
- **Input image maximum edge length**, under **Configuration**, remains configurable through `provider_settings.image_compress_options.max_size` (default 1280 pixels). Initial images keep their aspect ratio and are never enlarged. They may be reduced further to meet the byte limit. Images newly introduced by the request hook follow the same configured edge cap, format and animation handling, 64 MiB input limit, and strict 512 KiB output limit.
- Correctly oriented JPEG/PNG images already within both limits retain their original bytes. Other still images are orientation-corrected and encoded as JPEG, or PNG when they have transparency. Transparent images retain their alpha channel even when further reduction is necessary.
- GIF, animated WebP, and APNG inputs become a white 3×3 frame montage. Up to nine evenly spaced frames include the first and last animation frames; unused cells stay blank. An independent APNG cover is excluded.
- Unneeded metadata is removed when re-encoding. A color profile is retained when compatible with the output and the byte limit.

These limits also apply to user attachments in CUA sessions. Screenshot and other tool-result images keep their own handling.

## Configuration changes

| Previous setting | Current behavior |
| --- | --- |
| Enable image compression (`image_compress_enabled`) | Removed; current input images are always prepared. |
| JPEG quality (`image_compress_options.quality`) | Removed; output size is controlled automatically. |
| Maximum edge length (`image_compress_options.max_size`) | Renamed to **Input image maximum edge length**; applies together with the strict 512 KiB limit. |

Values of the removed settings in existing configuration files no longer affect image preparation.

## Original files and preview lifetime

In the legacy inline-image path, the image preparation stage adds ordinary `Image N` text notices with original paths and quoted-message origins. Numbers follow the image-block order after hooks and filtering, including image content parts before `image_urls`. No attachment metadata is added to request or message models. Quoted origins and successful caption results are passed directly from their processing steps; notice text is never parsed to infer state. Only notice objects generated by this request are refreshed after hooks, preserving plugin-supplied text. Skipped images keep an unnumbered reason and original path; animation labels identify the 3×3 montage. Images handled by a captioning model are marked as described in text, without taking a visual index in the main request.

`image_urls` and image content parts reuse compliant local JPEG/PNG files directly; no working copy is created. Images requiring conversion use prepared preview files. The attachment paths shown to the model for file access continue to point to the **original images**, so tools can read the originals. Original files and event image components are not overwritten.

Preview files are owned by the current event and deleted when the event finishes, including failure or cancellation. There is no shared image-conversion cache. Repeated references within one request reuse the same preview, including the preparation pass after the request hook.

In the legacy path, successfully localized original attachments, including quoted images, survive event cleanup. Retained originals under the temporary directory remain subject to `temp_dir_max_size` cleanup and are not permanent storage. Sources that have not yet been successfully adopted when request collection fails remain event-owned.

When persistent image context is explicitly disabled, the legacy path captures prepared images as Base64 data URIs before previews expire and does not migrate old history. The default path stores gallery references and migrates recoverable images when continuing old conversations. An unreadable image is skipped; valid text and other images remain. Cancellation, resource exhaustion, and programming errors are not treated as bad images.

Third-party Agent backends, direct provider calls that bypass the main-agent builder, and tool-result images are outside this input preparation flow.

## Persistent image gallery

The built-in agent stores incoming and tool-generated images under the AstrBot data directory's `image_assets/`. Conversation history stores lightweight `image_ref` records instead of original image bytes. The gallery is enabled by default (`provider_settings.image_context_enabled=true`); an explicit `false` retains the legacy inline-image path.

At the model request boundary, references that remain in history are authorized against the current conversation and restored to prepared visual inputs in their original message positions. The gallery does not generate additional descriptions, replace images with descriptions, or install image catalog, annotation, or review tools. An explicitly nonvisual provider receives an unavailable-vision notice; the gallery does not add a separate description-model call. Existing legacy caption settings outside the gallery path retain their own behavior.

This separates local storage from model input; it does not remove historical images from visual context. A later text-only user message can still send images that remain in its history, consuming image input tokens and request bytes. References removed from active history by normal context compression remain associated with the conversation, but are not automatically reinserted into subsequent requests. This feature does not implement provider Files API IDs or provider-side context caching. Providers continue using their existing image transport.

Image labels expose conversation-scoped occurrence IDs, not disk paths. `send_message_to_user` accepts an image occurrence ID from the current conversation to send its stored original without a model vision call for that send. Access is checked again before transmission. A request checks authorization before supported provider SDK attempts, including retries; adapters that cannot perform this check do not receive managed images.

Branches share immutable image assets while keeping separate conversation associations. Regeneration, editing, reset and deletion update the associations transactionally. Automatic garbage collection removes explicitly released final references; originals that were never associated remain for explicit maintenance. Original reads verify managed paths and file integrity. Older description metadata may be retained for stored-format compatibility, but it is not generated or used as model context by the gallery.

The gallery adds no total-capacity or per-original byte quota. Validation enforces at most 20 million pixels per frame and 100 frames per image. Visual requests have no additional image-count or combined Base64 byte cap. Existing model preparation still skips inputs larger than 64 MiB and produces previews strictly smaller than 512 KiB. Unavailable or unsaved images produce concise handling facts for the active persona; failures do not cause the gallery to claim that an image was saved.

## Legacy conversations and backups

Keep a complete backup before upgrading. Continuing a legacy conversation migrates recoverable embedded images and accessible AstrBot temporary-directory files into the gallery, without a confirmation popup, a startup-wide rewrite, or a description model call. Recovered bytes are marked `legacy_model_input`; they may be old resized previews rather than original uploads. The migration does not fetch remote URLs or arbitrary server files.

History and image associations commit together after source-snapshot verification. Failed migration preserves old history and prevents that turn from overwriting it. Published but unassociated files follow the explicit orphan-cleanup policy.

Online history reads and migration are limited to **16 MiB of stored UTF-8 JSON**, checked before materializing the history in Python. Oversized conversations remain listed and can be renamed or deleted; opening history, continuing chat, branching and online export are rejected. Full online backup also fails explicitly for oversized history. This branch does not include an offline migration tool for oversized histories.

Backups and portable conversation archives include the associated gallery assets. Plain JSONL alone does not contain original image files. Disabling the gallery does not expand persisted references back into Base64. Downgrading to a version without image-reference support requires restoring a complete pre-migration backup.
